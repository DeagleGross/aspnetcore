# September 28: lifecycle correctness, TCP churn, and final-send batching

[History index](README.md)

This day produced the strongest connection-churn improvement, but only after separating three problems: redundant TLS reads, a rejected-accept ownership leak, and the timing of response completion relative to FIN.

## Stop treating a returned plaintext page as socket readiness

The fd-TLS engine previously drove `SSL_read_ex` when managed code returned a consumed page, even when there was no buffered TLS input or paused read to resume. The new guard preserved progress for handshake/output/close work, buffered input, and backpressure resumption, but otherwise kept the readiness watch armed.

The first attempt stalled the slow-reader pipeline. `SSL_has_pending` can be false while additional records remain unread in the socket, so reaching the fourth leased page must preserve `read_backpressured` independently of that query. The corrected guard passed the pipeline and close checks.

In the fixed-library matched comparison, userspace fd TLS keep-alive improved from about 140,097 to 149,144 RPS (+6.5%); required kTLS improved from 126,234 to 134,638 (+6.7%). The stronger mechanism evidence was roughly two `SSL_read_ex` attempts per successful read becoming roughly one. kTLS still did not overtake the equivalent userspace TLS path.

Subsequent matrices standardized the client/server library selection. A library-version change alone had not explained the native transport results; it was not treated as the main optimization.

## The apparent coalescing shutdown problem was rejected-accept ownership

A full matrix exposed TLS short-run shutdown hangs and incomplete accounting. Captured pumps were still advancing, queues were empty, and native operations/leases had drained. The problem was not the wake-coalescing race from the original September 19 backend.

A socket could finish its TLS handshake after listener unbinding had closed the accepted-connection channel. The newer engine created the managed connection and then rejected the channel write. Calling `Abort` was insufficient: Kestrel never received the connection, so no consumer would dispose it or remove its native/dictionary ownership.

The engine now disposes rejected connections asynchronously, tracks those disposals until completion, and does not block the pump while waiting. Final native/managed reporting was also serialized to avoid interleaved JSON, and the runner now fails when server cleanup fails.

The faithful check gated real TLS client handshake writes across `UnbindAsync`. All four fd/BIO x coalescing-off/on cases timed out before the fix and passed afterward, disposing all 16 rejected connections per case. Later load runs actually exercised late rejection and drained. The misleading commit title `fix coalesce wakes problems` must not be read as evidence that the newer coalescing algorithm itself caused those hangs.

This was a correctness repair. Failed-cleanup RPS was excluded rather than turned into a performance claim.

## Why raw TCP short RPS was low

The new raw transport repeatedly achieved only about 38k-46k short-connection RPS against stock's roughly 52k-72k. At equal 30k offered load, both were close to 29.2k with similar server CPU/request, so the high-load gap was not a demonstrated intrinsic 40k server limit.

Targeted kernel profiling found substantial client work in source-port/connection lookup and reuse: `__inet_hash_connect`, `__inet_check_established`, locks, and `tcp_twsk_unique`. Against the new transport, the client used approximately 158-160 system CPU seconds in a 15-second run and accumulated about 13.5k client-side TIME_WAIT entries. Stock had much less client-side TIME_WAIT and client kernel CPU.

An isolated eight-source-address client removed much of that pressure without changing the servers. In two reversed-order, clean-state comparisons, unchanged io_uring averaged about 65,884 RPS against stock 60,752, with no TIME_WAIT overflow. This was a diagnostic intervention, not a replacement for the original client or proof of universal server superiority.

The original client reconnects as soon as it parses a close response. If it sees the response before the server's FIN, it can close first and retain source-port/TIME_WAIT state. The prototype's send completion -> managed continuation -> queued native close path provided a plausible avoidable delay.

Immediate small sends, skipping explicit receive cancellation, nonblocking accepted sockets, fewer connections, and a single pump did not independently solve the original single-source regression.

## Final-send plus shutdown: linking alone was insufficient

The output adapter can know that a send is final only when its real `PipeReader` result is completed, not canceled, and the segment is the last nonempty segment. No HTTP header parsing or one-response-per-connection assumption was added.

```text
Previous:
    final bytes -> send completion -> managed continuation -> queued close -> FIN

Raw TCP mode 3:
    known-final SEND(MSG_WAITALL | MSG_MORE) -> linked SHUTDOWN(SHUT_WR)
    terminal send/shutdown/read/cancel completions -> safe resource disposal
```

| Experiment | Observed TCP short RPS | Lesson |
|---|---:|---|
| Native shutdown immediately after final-send CQE, mode 1 | About 50k, one-run screen | Removing a managed round trip helped, but was not the full answer. |
| Linked final send/shutdown without `MSG_MORE`, mode 2 | About 39k, one-run screen | A link alone could still let the response reach the client before FIN. |
| Linked send/shutdown plus `MSG_MORE`, final drain-aware mode 3 | 84,008 / 85,485 | Deferring the known-final TCP tail materially improved this workload. |
| Default control, surrounding runs | About 39k-46k | The optimized result was roughly twice the previous throughput in this setting. |

Client-side TIME_WAIT fell to 31 / 62, and client system CPU to about 67-69 seconds per 15-second run. These results used the original single-source-address client. Response/FIN sequencing had a real end-to-end performance consequence.

The link is to write shutdown, not early descriptor close. Both SQEs are reserved/prepared together. A short `MSG_WAITALL` send cancels the shutdown successor; remaining bytes are retried only after the relevant completions drain. A managed close arriving before the linked shutdown CQE must not issue a competing shutdown.

The two final raw TCP runs still observed 140 / 64 `ENOTCONN` shutdown results among roughly 1.4 million links each. These remained classified and reported; they were not silently counted as successful shutdowns. Keep-alive's one-run off/on screen was about 218k/220k, not an established persistent-throughput gain.

## Extend the idea to fd TLS and the layered BIO

Fd TLS does not have an `SSL_write` SQE to link. Its implementation sets `TCP_CORK` before known-final application output, completes the OpenSSL write and `close_notify`, then initiates shutdown natively.

BIO TLS corks the socket, drains final application ciphertext through io_uring, generates and drains `close_notify` through the same BIO/send machinery, and then shuts down. Its plaintext mode closes natively after the final send drains. These BIO paths do not add a linked shutdown SQE.

This is equivalent in purpose, not identical machinery. Corking lets TCP defer the final tail; it does not guarantee that a whole response, TLS alert, and FIN occupy one packet. Descriptor/buffer lifetimes and partial-write handling remain intact.

Fresh off/on controls produced:

| Backend/workload | Batching off RPS | Batching on RPS | Approximate change |
|---|---:|---:|---:|
| BIO TCP short | 36,760 | 57,079 | +55.3% |
| BIO TCP long | 206,938 | 213,982 | +3.4% observed |
| Fd TLS short | 7,402 | 7,526 | +1.7% |
| Fd TLS long | 146,528 | 146,725 | +0.1% observed |
| BIO TLS short | 7,758 | 7,723 | -0.5% |
| BIO TLS long | 146,703 | 143,618 | -2.1% observed |

Each cell is a two-run mean with reversed order, except BIO TLS long, which has four runs per setting. All native runs used coalesced wakes. The same batch reran stock: about 51,082 TCP short, 180,554 TCP long, 4,330 TLS short, and 114,123 TLS long. These quick runs do not share the separate warmup procedure of the earlier raw TCP investigation.

The final TLS short path was reached on roughly 98% of application receives, with matching final-send, cork, alert, and native shutdown counts and no final-shutdown errors. Its small throughput change was not caused by failing to exercise the optimization.

Every keep-alive run reported zero final sends/corks. The observed persistent differences therefore do not demonstrate a final-tail batching benefit or delay. The repeated 2.1% lower BIO TLS result is retained as an observation with an unestablished cause, not dismissed as proven noise. Fresh full handshakes still occur on TLS short connections; no new CPU profile established their exact share of the remaining bottleneck.

## Lifetime evidence and retained choices

The final-output check exercised actual pipe completion, exact 1 KiB/4 MiB delivery before EOF, and reset cleanup in modes 0-3 across raw TCP, fd TLS, BIO TCP, BIO TLS, and required RX+TX kTLS. Its reset case was strengthened to 16 MiB output and a 4 KiB client receive buffer because the earlier default-buffer 4 MiB case could finish queueing before the intended reset.

Native ASan/UBSan runs covered final output and real Kestrel fragmented-body, persistent/pipelined, slow-reader, and peer-disconnect cases. An OpenSSL client observed the actual TLS close notification. Leak detection was disabled in the mixed managed/native process; these checks are not an exhaustive race or production-readiness proof. kTLS passed the new correctness path but was not rebenchmarked in this last batch.

The comparison convention is now coalesced wakes and final-send batching for native transports, with the fd read guard enabled. The environment switches remain opt-in in code: `NETWORKPROTO_COALESCE=1`, `NETWORKPROTO_FINAL_SEND=3`, and `NETWORKPROTO_GUARD_PAGE_READ=1` where applicable. Historical controls remain reproducible; there is no claim that every flag universally improves every workload.

The highest-confidence lesson is not simply "batch more." Avoid unnecessary scheduling and speculative work, keep ownership correct, and measure what the peer actually observes. On connection churn, the timing of the final response and FIN can dominate an apparently transport-local throughput regression.
