# September 27: custom BIO composition and verified kTLS

[History index](README.md)

## Make TLS a layer over completion-driven TCP

`IoUringBio` added a separate native engine behind the shared owned-page managed adapter. HTTP mode used raw TCP. HTTPS mode performed actual io_uring ciphertext receives and sends, with a custom OpenSSL source/sink BIO over transport-owned buffers.

Incoming ciphertext pages were queued without a memory-BIO staging copy. The BIO still copied into the destination OpenSSL requested; outgoing ciphertext was copied into stable asynchronous-send storage. Plaintext occupied a separate native page pool exposed directly to `PipeReader`.

This did not use `SSL_set_fd`, a socket BIO, or `BIO_s_mem`. The application send completed only after its generated ciphertext drained. Handshake output and `close_notify` used the same send machinery. The design made the copy and lifetime boundaries explicit instead of calling the whole path zero-copy.

## Matched userspace TLS comparison

Fresh controls, four server cores, twelve client cores, 1,200 connections, 1,024-byte response, 15-second runs, with native wake coalescing enabled. The primary TLS values were medians of three runs.

| Transport | TLS short RPS | TLS keep-alive RPS |
|---|---:|---:|
| Stock Sockets / SslStream | 3,930 | 128,650 |
| Fd-bound IoUringTls | 5,368 | 146,222 |
| Custom-BIO IoUringBio | 5,359 | 163,026 |

Custom BIO was essentially tied with fd TLS for short connections and about 11.5% ahead on keep-alive. Relative to stock, its medians were about +36% short and +27% persistent. Individual fd/BIO ranges overlapped; this was a promising result, not a universal architecture ranking.

A single plaintext screen still showed the unresolved churn problem: BIO 44,415 versus stock 65,911 RPS on short connections. BIO keep-alive was 225,150 versus stock 208,079 in that screen.

## kTLS really activated, but was not faster

The fd transport gained a required-kTLS mode. Every completed handshake in the accepted runs had both RX and TX active according to OpenSSL, corroborated by Linux TLS counters. Missing activation rejected the connection rather than silently producing a userspace-TLS benchmark.

This was software kernel TLS, not hardware NIC offload. A separate demonstration used a custom observing filter above OpenSSL's socket BIO; that filter preserved socket-specific kTLS controls. It was not the transport-neutral source/sink BIO used by `IoUringBio`.

The later evening matched batch gave:

| Fd transport configuration | TLS short RPS | TLS keep-alive RPS | Process CPU us/request, keep-alive |
|---|---:|---:|---:|
| Userspace TLS | 4,731 | 114,575 | 31.6 |
| Required and verified kTLS RX+TX | 4,707 | 102,020 | 34.6 |

Short throughput was essentially unchanged; persistent throughput was approximately 11% lower and process CPU/request about 9% higher with kTLS. Its improvement over stock in that same batch was not a kTLS-specific gain, because userspace native TLS was already faster.

The custom source/sink BIO reported RX=0/TX=0 and correctly rejected required-kTLS connections. It did not acquire kTLS support merely by setting an option. No fallback throughput was recorded as if kernel TLS had been used.

## Evidence and boundaries

See [the BIO architecture report](../../IoUringBio/README.md) and the September 27 custom-BIO/kTLS sections in [RPS-RESULTS](../RPS-RESULTS.md). Local aggregates are `layered-bio-comparison-20260927.json` and `ktls-comparison-20260927.json`; the activation evidence includes `ktls-activation-20260927-195802`.

Functional/native sanitizer checks covered fragmented bodies, 3,001 pipelined responses with a paused reader, actual partial ciphertext sends, peer disconnects, and continued service. Plaintext and ciphertext page accounting balanced in the accepted runs.

The BIO design reserved both plaintext and ciphertext page pools and still allocated roughly 4.1 KB/request managed memory. No complete explanation of the remaining kTLS cost was established. The next work targeted a concrete redundant-read path rather than assuming moving record processing into the kernel must win.
