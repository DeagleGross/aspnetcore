# September 25: standalone C experiments and the TLS I/O model

[History index](README.md)

The smaller C experiments isolated receive modes and TLS integration from Kestrel's managed scheduling and pipes. They live in the sibling `Network-Transport-Experiments/experiments/io-uring-http` directory. These were real implementations, not execution of the Orleans pull requests that helped motivate the design discussion.

## One-shot versus multishot receive

Four pinned, single-threaded server processes each owned their ring and shared the listening port with `SO_REUSEPORT`. Both receive variants used a provided-buffer pool. The first benchmark closed after one response, so a persistent receive had little opportunity to amortize its setup and still needed correct cancellation/draining.

| Offered RPS | One-shot median achieved RPS | Multishot median achieved RPS | Finding |
|---|---:|---:|---|
| 60,000 | 58,489 | 58,235 | About -0.4%; no demonstrated multishot advantage |
| 120,000 | 66,355 | 65,910 | About -0.7%; noisy and client-constrained |

These historical values precede the later HTTP-framing/keep-alive implementation and still used one-shot accept. The client consumed almost all of its four-core budget at the high offered rate while the server used about 1.8 cores in total. It was not a measurement of the maximum capacity of four server cores.

Both examples were subsequently given bounded HTTP framing, persistent connections, pipelining, and multishot accept. On persistent traffic, receive submissions could be amortized across multiple requests. The lifetime rule remained essential: a cancellation acknowledgment alone never releases the receive operation or its buffers.

Backward wall-clock adjustments also caused the original wrk2 timing assertions to fail. A monotonic-clock patch was used consistently for the accepted comparisons; crashed/unpatched runs were not presented as results.

## Two TLS paths with different ownership

The initial C BIO variant used memory BIOs: io_uring received ciphertext, the application fed it to OpenSSL, and drained encrypted output for io_uring sends. The fd variant used `SSL_set_fd`: OpenSSL performed the socket reads/writes, while io_uring waited for readiness when OpenSSL returned `WANT_READ` or `WANT_WRITE`.

Neither design submits `SSL_read` itself to the ring. A readiness CQE says that attempting I/O may make progress; it is not a received plaintext buffer. The later Kestrel custom source/sink BIO is also not the same implementation as this early memory-BIO baseline.

## Avoiding unnecessary TLS reads was better than adding ring features

The successful fd variant combined OpenSSL read-ahead with a readiness-directed retry policy. After a completed response, when neither HTTP nor OpenSSL had buffered input, it armed readiness rather than immediately making another `SSL_read` call that would usually return `WANT_READ`.

| Persistent TLS server | Median RPS, three runs |
|---|---:|
| Memory-BIO baseline | 296,339 |
| Original fd-bound TLS | 297,285 |
| Fd TLS with read-ahead | 313,381 |
| Read-ahead plus readiness-directed retry | 333,964 |

The final variant was approximately 12.3% above the original fd path and 12.7% above the BIO baseline. Reported fd read syscalls per response fell from roughly three to two to one across those stages. That is workload-specific accounting, not an API guarantee.

For short TLS connections, BIO versus the final fd variant was about 5,775 versus 5,854 RPS, only 1.4% with overlapping ranges. The keep-alive optimization did not establish a meaningful full-handshake throughput win.

Single-run screens of ring setup/combined waiting, persistent readiness polling, and an epoll/io_uring hybrid did not demonstrate a consistent improvement. Fewer registrations or submissions were not enough on their own.

## Evidence and boundaries

The [standalone experiment report at the recorded commit](https://github.com/DeagleGross/Network-Transport-Experiments/blob/d732fa2fd9c52eabf516a50700f4e8552ec5a0f0/experiments/io-uring-http/README.md) preserves the detailed architecture and measurements. The initial plaintext work is recorded in commit `62c4c40`; the expanded report was collected in `d732fa2` on September 26, but explicitly dates these measurements September 25.

Local raw directories include `tls-architecture-confirm-20260925-220150` and `tls-architecture-close-confirm-20260925-220934`. The TLS runs used twelve client cores, 1,200 connections, 15 seconds, and TLS 1.3 with an ECDSA certificate, unlike the later Kestrel TLS 1.2/RSA matrix. The C response was also smaller.

Functional and native sanitizer checks exercised fragmented input, persistence, EOF, partial sends, and TLS write retries. There was no kTLS or physical-NIC measurement. These were architecture experiments, not evidence that a 334k-RPS C server predicts equivalent Kestrel throughput.
