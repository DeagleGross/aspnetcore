# September 26: four native pumps, owned receive pages, and coalesced wakes

[History index](README.md)

The newer Kestrel backends addressed the older implementation's single-pump limit and the ownership boundary between native I/O and managed pipes. The original `io_uring` backend was preserved as a separate control.

## New transport architecture

`IoUringTcp` introduced four pinned native pump threads, multishot accept/receive, and native provided-buffer pages exposed through an owned `PipeReader`. Kestrel's ordinary managed scheduling and HTTP parsing remained. Received data no longer needed an additional adapter payload copy into pipe-owned storage.

`IoUringTls` used the same managed integration but terminated TLS natively through fd-bound OpenSSL. Multishot read-readiness polling and write readiness drove OpenSSL retries; `SSL_read_ex` wrote directly into native plaintext pages exposed to the reader. Kestrel consumed post-TLS plaintext and TLS features, not another `UseHttps`/SslStream layer.

Output pipe memory stayed pinned through native completion. These changes eliminated one receive-copy boundary, not every networking/TLS copy, and did not make ordinary sends multishot.

## Initial Kestrel results

Same application and 1,024-byte body, four server cores, twelve client cores, 1,200 connections, two 15-second wrk2 runs per cell. TLS used TLS 1.2/RSA/AES-128-GCM without resumption.

| Architecture before the separate coalescing comparison | TCP short RPS | TCP long RPS | TLS short RPS | TLS long RPS |
|---|---:|---:|---:|---:|
| Stock Sockets / SslStream | 55,956 | 166,011 | 3,342 | 109,143 |
| Original single-ring io_uring / SslStream | 33,821 | 72,658 | 3,108 | 63,120 |
| New IoUringTcp / SslStream | 41,849 | 200,273 | 3,543 | 125,866 |
| New fd-bound IoUringTls | N/A | N/A | 5,668 | 136,077 |

Against the initial stock controls, the new raw transport was about 21% ahead on TCP keep-alive and 15% ahead with SslStream keep-alive; fd TLS was about 70% ahead on short TLS and 25% on long TLS. TCP short was still about 25% behind stock.

A later unchanged stock control rose to about 183k TCP long and 130k TLS long. Against that control, the best prototype averages were only about 9% and 12% higher respectively. The reports preserve both comparisons instead of attributing environmental drift to implementation changes.

## Coalescing wakes: one pending notification can cover many commands

Without coalescing, cross-thread producers write eventfd repeatedly even when the pump already has work to process. The newer shared engine queues each command, but only the producer that changes the pending-wake marker from zero to one writes the notification. Additional commands share that pending wake. Pump-originated commands do not wake the thread already processing them.

The pump clears the marker before draining the queue. A concurrent producer therefore either contributes to that drain or leaves a notification for the next native wait. No intentional delay is added to accumulate a batch, and buffer/completion ownership is unchanged.

This is a scheduling optimization of the same transport, not a separate TLS or io_uring architecture.

| Same newer backend, coalescing disabled -> enabled | Before RPS | After RPS | Approximate change |
|---|---:|---:|---:|
| IoUringTcp, TCP keep-alive | 200,273 | 193,789 | -3.2% |
| IoUringTcp / SslStream, TLS keep-alive | 125,866 | 137,807 | +9.5% |
| IoUringTls, TLS keep-alive | 136,077 | 145,915 | +7.2% |
| IoUringTls, TLS short | 5,668 | 5,429 | -4.2% |

The important result is reduced redundant notification work with mixed RPS effects, not a claim that every workload got faster. A later September 28 matched matrix also showed roughly 5% higher TCP keep-alive and 10% higher fd TLS keep-alive with coalescing, but short-run drift and cleanup failures in other cells required care.

Example coalesced runs used about 0.115 pump-step plus wake P/Invokes per TCP request and 0.102 per fd-TLS request, with about 1,200 receive/readiness submissions servicing millions of persistent requests. These are specific interop counters, not every syscall and not a measured before/after reduction factor.

## Remaining cost and evidence

The newer adapter still allocated roughly 4.0-4.3 KB per keep-alive request versus 1.6-1.7 KB for stock. Native page storage was 32 MiB per worker, with per-page wrappers, task completions, and cross-thread commands still present. The architectural improvement was not an allocation improvement over the older reusable-operation prototype.

See [RPS-RESULTS](../RPS-RESULTS.md), its original September 26 setup/tables, and [the sample report](../../../../samples/NetworkProtoSample/RESULTS.md). Raw evidence is `NetworkProtoSample/results/quick-*-20260926-*` and `quick-comparison-20260926.json`.

Real Kestrel fragmented input, page-boundary headers, 132-request reuse/pipelining, explicit close, and page-return accounting were exercised. One contaminated original-backend short run was excluded. The large TCP-short deficit remained an open investigation, not an accepted permanent cost of io_uring.
